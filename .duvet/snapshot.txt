    TEXT[!MUST]:    An intermediary MUST NOT forward a message to itself unless it is
    TEXT[!MUST]:    protected from an infinite request loop.

  SECTION: [Connection](#section-7.6.1)
    TEXT[!MUST]:    When a field aside from Connection is used to supply control
    TEXT[!MUST]:    information for or about the current connection, the sender MUST list
    TEXT[!MUST]:    the corresponding field name within the Connection header field.
    TEXT[!MUST]:    Intermediaries MUST parse a received Connection header field before a
    TEXT[!MUST]:    message is forwarded and, for each connection-option in this field,
    TEXT[!MUST]:    remove any header or trailer field(s) from the message with the same
    TEXT[!MUST]:    name as the connection-option, and then remove the Connection header
    TEXT[!MUST]:    field itself (or replace it with the intermediary's own control
    TEXT[!MUST]:    options for the forwarded message).
    TEXT[!SHOULD]:    Furthermore, intermediaries SHOULD remove or replace fields that are
    TEXT[!SHOULD]:    known to require removal before forwarding, whether or not they
    TEXT[!SHOULD]:    appear as a connection-option, after applying those fields'
    TEXT[!SHOULD]:    semantics.
    TEXT[!MUST]:    A sender MUST NOT send a connection option corresponding to a field
    TEXT[!MUST]:    that is intended for all recipients of the content.

  SECTION: [Max-Forwards](#section-7.6.2)
    TEXT[!MUST]:    Each intermediary that receives a TRACE or OPTIONS request containing
    TEXT[!MUST]:    a Max-Forwards header field MUST check and update its value prior to
    TEXT[!MUST]:    forwarding the request.
    TEXT[!MUST]: If the received value is zero (0), the
    TEXT[!MUST]:    intermediary MUST NOT forward the request; instead, the intermediary
    TEXT[!MUST]:    MUST respond as the final recipient.
    TEXT[!MUST]: If the received Max-Forwards
    TEXT[!MUST]:    value is greater than zero, the intermediary MUST generate an updated
    TEXT[!MUST]:    Max-Forwards field in the forwarded message with a field value that
    TEXT[!MUST]:    is the lesser of a) the received value decremented by one (1) or b)
    TEXT[!MUST]:    the recipient's maximum supported value for Max-Forwards.
    TEXT[!MAY]:    A recipient MAY ignore a Max-Forwards header field received with any
    TEXT[!MAY]:    other request methods.

  SECTION: [Via](#section-7.6.3)
    TEXT[!MUST]:    A proxy MUST send an appropriate Via header field, as described
    TEXT[!MUST]:    below, in each message that it forwards.
    TEXT[!MUST]: An HTTP-to-HTTP gateway
    TEXT[!MUST]:    MUST send an appropriate Via header field in each inbound request
    TEXT[!MUST]:    message and MAY send a Via header field in forwarded response
    TEXT[!MUST]:    messages.
    TEXT[!MAY]: However, if the real host is considered to be sensitive
    TEXT[!MAY]:    information, a sender MAY replace it with a pseudonym.
    TEXT[!MAY]: If a port is
    TEXT[!MAY]:    not provided, a recipient MAY interpret that as meaning it was
    TEXT[!MAY]:    received on the default port, if any, for the received-protocol.
    TEXT[!MAY]:    A sender MAY generate comments to identify the software of each
    TEXT[!MAY]:    recipient, analogous to the User-Agent and Server header fields.
    TEXT[!MAY]:    However, comments in Via are optional, and a recipient MAY remove
    TEXT[!MAY]:    them prior to forwarding the message.
    TEXT[!SHOULD]:    An intermediary used as a portal through a network firewall SHOULD
    TEXT[!SHOULD]:    NOT forward the names and ports of hosts within the firewall region
    TEXT[!SHOULD]:    unless it is explicitly enabled to do so.
    TEXT[!SHOULD]: If not enabled, such an
    TEXT[!SHOULD]:    intermediary SHOULD replace each received-by host of any host behind
    TEXT[!SHOULD]:    the firewall by an appropriate pseudonym for that host.
    TEXT[!MAY]:    An intermediary MAY combine an ordered subsequence of Via header
    TEXT[!MAY]:    field list members into a single member if the entries have identical
    TEXT[!MAY]:    received-protocol values.
    TEXT[!SHOULD]:    A sender SHOULD NOT combine multiple list members unless they are all
    TEXT[!SHOULD]:    under the same organizational control and the hosts have already been
    TEXT[!SHOULD]:    replaced by pseudonyms.
    TEXT[!MUST]: A sender MUST NOT combine members that have
    TEXT[!MUST]:    different received-protocol values.

  SECTION: [Message Transformations](#section-7.7)
    TEXT[!MAY]:    If a proxy receives a target URI with a host name that is not a fully
    TEXT[!MAY]:    qualified domain name, it MAY add its own domain to the host name it
    TEXT[!MAY]:    received when forwarding the request.
    TEXT[!MUST]: A proxy MUST NOT change the
    TEXT[!MUST]:    host name if the target URI contains a fully qualified domain name.
    TEXT[!MUST]:    A proxy MUST NOT modify the "absolute-path" and "query" parts of the
    TEXT[!MUST]:    received target URI when forwarding it to the next inbound server
    TEXT[!MUST]:    except as required by that forwarding protocol.
    TEXT[!MUST]:    A proxy MUST NOT transform the content (Section 6.4) of a response
    TEXT[!MUST]:    message that contains a no-transform cache directive (Section 5.2.2.6
    TEXT[!MUST]:    of [CACHING]).
    TEXT[!MAY]:    A proxy MAY transform the content of a message that does not contain
    TEXT[!MAY]:    a no-transform cache directive.
    TEXT[!SHOULD]:    A proxy SHOULD NOT modify header fields that provide information
    TEXT[!SHOULD]:    about the endpoints of the communication chain, the resource state,
    TEXT[!SHOULD]:    or the selected representation (other than the content) unless the
    TEXT[!SHOULD]:    field's definition specifically allows such modification or the
    TEXT[!SHOULD]:    modification is deemed necessary for privacy or security.

  SECTION: [Upgrade](#section-7.8)
    TEXT[!MAY]:    A client MAY send a list of protocol names in the Upgrade header
    TEXT[!MAY]:    field of a request to invite the server to switch to one or more of
    TEXT[!MAY]:    the named protocols, in order of descending preference, before
    TEXT[!MAY]:    sending the final response.
    TEXT[!MAY]: A server MAY ignore a received Upgrade
    TEXT[!MAY]:    header field if it wishes to continue using the current protocol on
    TEXT[!MAY]:    that connection.
    TEXT[!SHOULD]:    Although protocol names are registered with a preferred case,
    TEXT[!SHOULD]:    recipients SHOULD use case-insensitive comparison when matching each
    TEXT[!SHOULD]:    protocol-name to supported protocols.
    TEXT[!MUST]:    A server that sends a 101 (Switching Protocols) response MUST send an
    TEXT[!MUST]:    Upgrade header field to indicate the new protocol(s) to which the
    TEXT[!MUST]:    connection is being switched; if multiple protocol layers are being
    TEXT[!MUST]:    switched, the sender MUST list the protocols in layer-ascending
    TEXT[!MUST]:    order.
    TEXT[!MUST]: A server MUST NOT switch to a protocol that was not indicated
    TEXT[!MUST]:    by the client in the corresponding request's Upgrade header field.
    TEXT[!MAY]:    server MAY choose to ignore the order of preference indicated by the
    TEXT[!MAY]:    client and select the new protocol(s) based on other factors, such as
    TEXT[!MAY]:    the nature of the request or the current load on the server.
    TEXT[!MUST]:    A server that sends a 426 (Upgrade Required) response MUST send an
    TEXT[!MUST]:    Upgrade header field to indicate the acceptable protocols, in order
    TEXT[!MUST]:    of descending preference.
    TEXT[!MAY]:    A server MAY send an Upgrade header field in any other response to
    TEXT[!MAY]:    advertise that it implements support for upgrading to the listed
    TEXT[!MAY]:    protocols, in order of descending preference, when appropriate for a
    TEXT[!MAY]:    future request.
    TEXT[!MUST]: A server MUST NOT switch protocols
    TEXT[!MUST]:    unless the received message semantics can be honored by the new
    TEXT[!MUST]:    protocol; an OPTIONS request can be honored by any protocol.
    TEXT[!MUST]:    A sender of Upgrade MUST also send an "Upgrade" connection option in
    TEXT[!MUST]:    the Connection header field (Section 7.6.1) to inform intermediaries
    TEXT[!MUST]:    not to forward this field.
    TEXT[!MUST]: A server that receives an Upgrade header
    TEXT[!MUST]:    field in an HTTP/1.0 request MUST ignore that Upgrade field.
    TEXT[!MUST]:    If a server receives both an Upgrade and an Expect header field with
    TEXT[!MUST]:    the "100-continue" expectation (Section 10.1.1), the server MUST send
    TEXT[!MUST]:    a 100 (Continue) response before sending a 101 (Switching Protocols)
    TEXT[!MUST]:    response.

    TEXT[!SHOULD]:    a Content-Type header field in that message unless the intended media

    TEXT[!MAY]: If a
    TEXT[!MAY]:    Content-Type header field is not present, the recipient MAY either

    TEXT[!MAY]:    (Section 5.6.6) in the form of name/value pairs.

    TEXT[!MUST]: The message body is itself a protocol element; a sender MUST
    TEXT[!MUST]:    generate only CRLF to represent line breaks between body parts.

    TEXT[!MUST]:    If one or more encodings have been applied to a representation, the

    TEXT[!SHOULD]: Note that the coding named "identity" is reserved
    TEXT[!SHOULD]:    for its special role in Accept-Encoding and thus SHOULD NOT be
    TEXT[!SHOULD]:    included.
    TEXT[!MAY]:    An origin server MAY respond with a status code of 415 (Unsupported
    TEXT[!MAY]:    Media Type) if a representation in the request message has a content

    TEXT[!MAY]:    Multiple languages MAY be listed for content that is intended for

  SECTION: [Content-Length](#section-8.6)
    TEXT[!SHOULD]:    A user agent SHOULD send Content-Length in a request when the method
    TEXT[!SHOULD]:    defines a meaning for enclosed content and it is not sending
    TEXT[!SHOULD]:    Transfer-Encoding.
    TEXT[!SHOULD]: A user agent SHOULD NOT send a Content-Length header field
    TEXT[!SHOULD]:    when the request message does not contain content and the method
    TEXT[!SHOULD]:    semantics do not anticipate such data.
    TEXT[!MUST]:    A server MAY send a Content-Length header field in a response to a
    TEXT[!MUST]:    HEAD request (Section 9.3.2); a server MUST NOT send Content-Length
    TEXT[!MUST]:    in such a response unless its field value equals the decimal number
    TEXT[!MUST]:    of octets that would have been sent in the content of a response if
    TEXT[!MUST]:    the same request had used the GET method.
    TEXT[!MUST]:    A server MAY send a Content-Length header field in a 304 (Not
    TEXT[!MUST]:    Modified) response to a conditional GET request (Section 15.4.5); a
    TEXT[!MUST]:    server MUST NOT send Content-Length in such a response unless its
    TEXT[!MUST]:    field value equals the decimal number of octets that would have been
    TEXT[!MUST]:    sent in the content of a 200 (OK) response to the same request.
    TEXT[!MUST]:    A server MUST NOT send a Content-Length header field in any response
    TEXT[!MUST]:    with a status code of 1xx (Informational) or 204 (No Content).
    TEXT[!MUST]:    server MUST NOT send a Content-Length header field in any 2xx
    TEXT[!MUST]:    (Successful) response to a CONNECT request (Section 9.3.6).
    TEXT[!SHOULD]:    Aside from the cases defined above, in the absence of Transfer-
    TEXT[!SHOULD]:    Encoding, an origin server SHOULD send a Content-Length header field
    TEXT[!SHOULD]:    when the content size is known prior to sending the complete header
    TEXT[!SHOULD]:    section.
    TEXT[!MUST]: Since there is no predefined limit to the length of content,
    TEXT[!MUST]:    a recipient MUST anticipate potentially large decimal numerals and
    TEXT[!MUST]:    prevent parsing errors due to integer conversion overflows or
    TEXT[!MUST]:    precision loss due to integer conversion (Section 17.5).
    TEXT[!MUST]:    As a result, a sender MUST NOT forward a message with a Content-
    TEXT[!MUST]:    Length header field value that is known to be incorrect.
    TEXT[!MUST]:    Likewise, a sender MUST NOT forward a message with a Content-Length
    TEXT[!MUST]:    header field value that does not match the ABNF above, with one
    TEXT[!MUST]:    exception: a recipient of a Content-Length header field value
    TEXT[!MUST]:    consisting of the same decimal value repeated as a comma-separated
    TEXT[!MUST]:    list (e.g, "Content-Length: 42, 42") MAY either reject the message as
    TEXT[!MUST]:    invalid or replace that invalid field value with a single instance of
    TEXT[!MUST]:    the decimal value, since this likely indicates that a duplicate was
    TEXT[!MUST]:    generated or combined by an upstream message processor.

  SECTION: [Content-Location](#section-8.7)
    TEXT[!MAY]:    If Content-Location is included in a 2xx (Successful) response
    TEXT[!MAY]:    message and its value refers (after conversion to absolute form) to a
    TEXT[!MAY]:    URI that is the same as the target URI, then the recipient MAY
    TEXT[!MAY]:    consider the content to be a current representation of that resource
    TEXT[!MAY]:    at the time indicated by the message origination date.
    TEXT[!MUST]:    An origin server that receives a Content-Location field in a request
    TEXT[!MUST]:    message MUST treat the information as transitory request context
    TEXT[!MUST]:    rather than as metadata to be saved verbatim as part of the
    TEXT[!MUST]:    representation.
    TEXT[!MAY]: An origin server MAY use that context to guide in
    TEXT[!MAY]:    processing the request or to save it for other uses, such as within
    TEXT[!MAY]:    source links or versioning metadata.
    TEXT[!MUST]: However, an origin server MUST
    TEXT[!MUST]:    NOT use such context information to alter the request semantics.

  SECTION: [Weak versus Strong](#section-8.8.1)

    TEXT[!SHOULD]:    for the current representation.

  SECTION: [Generation](#section-8.8.2.1)
    TEXT[!SHOULD]:    An origin server SHOULD send Last-Modified for any selected
    TEXT[!SHOULD]:    representation for which a last modification date can be reasonably
    TEXT[!SHOULD]:    and consistently determined, since its use in conditional requests
    TEXT[!SHOULD]:    and evaluating cache freshness ([CACHING]) can substantially reduce
    TEXT[!SHOULD]:    unnecessary transfers and significantly improve service availability
    TEXT[!SHOULD]:    and scalability.
    TEXT[!SHOULD]:    An origin server SHOULD obtain the Last-Modified value of the
    TEXT[!SHOULD]:    representation as close as possible to the time that it generates the
    TEXT[!SHOULD]:    Date field value for its response.
    TEXT[!MUST]:    An origin server with a clock (as defined in Section 5.6.7) MUST NOT
    TEXT[!MUST]:    generate a Last-Modified date that is later than the server's time of
    TEXT[!MUST]:    message origination (Date, Section 6.6.1).
    TEXT[!MUST]: If the last modification
    TEXT[!MUST]:    time is derived from implementation-specific metadata that evaluates
    TEXT[!MUST]:    to some time in the future, according to the origin server's clock,
    TEXT[!MUST]:    then the origin server MUST replace that value with the message
    TEXT[!MUST]:    origination date.
    TEXT[!MUST]:    An origin server without a clock MUST NOT generate a Last-Modified
    TEXT[!MUST]:    date for a response unless that date value was assigned to the
    TEXT[!MUST]:    resource by some other system (presumably one with a clock).

    TEXT[!MAY]:    All other methods are OPTIONAL.

    TEXT[!SHOULD]:    request method that is unrecognized or not implemented SHOULD respond

    TEXT[!SHOULD]:    made aware of an unsafe action before it is requested.

    TEXT[!MUST]:    resource is to perform an unsafe action, then the resource owner MUST
    TEXT[!MUST]:    disable or disallow that action when it is accessed using a safe
    TEXT[!MUST]:    request method.

  SECTION: [Idempotent Methods](#section-9.2.2)
    TEXT[implementation,test]: Of the request methods
    TEXT[implementation,test]:    defined by this specification, PUT, DELETE, and safe request methods
    TEXT[implementation,test]:    are idempotent.

    TEXT[!SHOULD]:    idempotent method unless it has some means to know that the request

  SECTION: [GET](#section-9.3.1)
    TEXT[!SHOULD]: A client SHOULD NOT generate content in a GET
    TEXT[!SHOULD]:    request unless it is made directly to an origin server that has
    TEXT[!SHOULD]:    previously indicated, in or out of band, that such a request has a
    TEXT[!SHOULD]:    purpose and will be adequately supported.

    TEXT[!SHOULD]:    NOT rely on private agreements to receive content, since participants
    TEXT[!SHOULD]:    in HTTP communication are often unaware of intermediaries along the
    TEXT[!SHOULD]:    request chain.
    TEXT[!MAY]:    The response to a GET request is cacheable; a cache MAY use it to
    TEXT[!MAY]:    satisfy subsequent GET and HEAD requests unless otherwise indicated
    TEXT[!MAY]:    by the Cache-Control header field (Section 5.2 of [CACHING]).

    TEXT[!MUST]:    send content in the response.
    TEXT[!SHOULD]:    The server SHOULD send the same header fields in response to a HEAD
    TEXT[!SHOULD]:    request as it would have sent if the request method had been GET.
    TEXT[!MAY]:    However, a server MAY omit header fields for which a value is
    TEXT[!MAY]:    determined only while generating the content.
    TEXT[!SHOULD]: A client SHOULD NOT generate content
    TEXT[!SHOULD]:    in a HEAD request unless it is made directly to an origin server that
    TEXT[!SHOULD]:    has previously indicated, in or out of band, that such a request has
    TEXT[!SHOULD]:    a purpose and will be adequately supported.
    TEXT[!SHOULD]: An origin server SHOULD
    TEXT[!SHOULD]:    NOT rely on private agreements to receive content, since participants
    TEXT[!SHOULD]:    in HTTP communication are often unaware of intermediaries along the
    TEXT[!SHOULD]:    request chain.
    TEXT[!MAY]:    The response to a HEAD request is cacheable; a cache MAY use it to
    TEXT[!MAY]:    satisfy subsequent HEAD requests unless otherwise indicated by the
    TEXT[!MAY]:    Cache-Control header field (Section 5.2 of [CACHING]).

  SECTION: [POST](#section-9.3.3)
    TEXT[!SHOULD]:    If one or more resources has been created on the origin server as a
    TEXT[!SHOULD]:    result of successfully processing a POST request, the origin server
    TEXT[!SHOULD]:    SHOULD send a 201 (Created) response containing a Location header
    TEXT[!SHOULD]:    field that provides an identifier for the primary resource created
    TEXT[!SHOULD]:    (Section 10.2.2) and a representation that describes the status of
    TEXT[!SHOULD]:    the request while referring to the new resource(s).
    TEXT[!MAY]:    If the result of processing a POST would be equivalent to a
    TEXT[!MAY]:    representation of an existing resource, an origin server MAY redirect
    TEXT[!MAY]:    the user agent to that resource by sending a 303 (See Other) response
    TEXT[!MAY]:    with the existing resource's identifier in the Location field.

  SECTION: [PUT](#section-9.3.4)
    TEXT[!MUST]:    If the target resource does not have a current representation and the
    TEXT[!MUST]:    PUT successfully creates one, then the origin server MUST inform the
    TEXT[!MUST]:    user agent by sending a 201 (Created) response.
    TEXT[!MUST]: If the target
    TEXT[!MUST]:    resource does have a current representation and that representation
    TEXT[!MUST]:    is successfully modified in accordance with the state of the enclosed
    TEXT[!MUST]:    representation, then the origin server MUST send either a 200 (OK) or
    TEXT[!MUST]:    a 204 (No Content) response to indicate successful completion of the
    TEXT[!MUST]:    request.
    TEXT[!SHOULD]:    An origin server SHOULD verify that the PUT representation is
    TEXT[!SHOULD]:    consistent with its configured constraints for the target resource.
    TEXT[!SHOULD]: When a PUT representation is
    TEXT[!SHOULD]:    inconsistent with the target resource, the origin server SHOULD
    TEXT[!SHOULD]:    either make them consistent, by transforming the representation or
    TEXT[!SHOULD]:    changing the resource configuration, or respond with an appropriate
    TEXT[!SHOULD]:    error message containing sufficient information to explain why the
    TEXT[!SHOULD]:    representation is unsuitable.
    TEXT[!SHOULD]: As a
    TEXT[!SHOULD]:    result, an origin server SHOULD ignore unrecognized header and
    TEXT[!SHOULD]:    trailer fields received in a PUT request (i.e., not save them as part
    TEXT[!SHOULD]:    of the resource state).
    TEXT[!MUST]:    An origin server MUST NOT send a validator field (Section 8.8), such
    TEXT[!MUST]:    as an ETag or Last-Modified field, in a successful response to PUT
    TEXT[!MUST]:    unless the request's representation data was saved without any
    TEXT[!MUST]:    transformation applied to the content (i.e., the resource's new
    TEXT[!MUST]:    representation data is identical to the content received in the PUT
    TEXT[!MUST]:    request) and the validator field value reflects the new
    TEXT[!MUST]:    representation.
    TEXT[!SHOULD]: A service that selects a
    TEXT[!SHOULD]:    proper URI on behalf of the client, after receiving a state-changing
    TEXT[!SHOULD]:    request, SHOULD be implemented using the POST method rather than PUT.
    TEXT[!MUST]:    If the origin server will not make the requested PUT state change to
    TEXT[!MUST]:    the target resource and instead wishes to have it applied to a
    TEXT[!MUST]:    different resource, such as when the resource has been moved to a
    TEXT[!MUST]:    different URI, then the origin server MUST send an appropriate 3xx
    TEXT[!MUST]:    (Redirection) response; the user agent MAY then make its own decision
    TEXT[!MUST]:    regarding whether or not to redirect the request.

  SECTION: [CONNECT](#section-9.3.6)
    TEXT[implementation]:    CONNECT uses a special form of request target, unique to this method,
    TEXT[implementation]:    consisting of only the host and port number of the tunnel
    TEXT[implementation]:    destination, separated by a colon.
    TEXT[!MUST]: There is no default port; a
    TEXT[!MUST]:    client MUST send the port number even if the CONNECT request is based
    TEXT[!MUST]:    on a URI reference that contains an authority component with an
    TEXT[!MUST]:    elided port (Section 4.1).
    TEXT[!MUST,implementation,test]:    A server MUST reject a CONNECT request that targets an empty or
    TEXT[!MUST,implementation,test]:    invalid port number
    TEXT[!MUST,implementation]: , typically by responding with a 400 (Bad Request)
    TEXT[!MUST,implementation]:    status code.
    TEXT[!MAY]:    An origin server MAY accept a CONNECT request, but most origin
    TEXT[!MAY]:    servers do not implement CONNECT.
    TEXT[!MUST]:    A tunnel is closed when a tunnel intermediary detects that either
    TEXT[!MUST]:    side has closed its connection: the intermediary MUST attempt to send
    TEXT[!MUST]:    any outstanding data that came from the closed side to the other
    TEXT[!MUST]:    side, close both connections, and then discard any remaining data
    TEXT[!MUST]:    left undelivered.
    TEXT[!SHOULD]: Proxies that support CONNECT SHOULD
    TEXT[!SHOULD]:    restrict its use to a limited set of known ports or a configurable
    TEXT[!SHOULD]:    list of safe request targets.
    TEXT[!MUST]:    A server MUST NOT send any Transfer-Encoding or Content-Length header
    TEXT[!MUST]:    fields in a 2xx (Successful) response to CONNECT.
    TEXT[!MUST]: A client MUST
    TEXT[!MUST]:    ignore any Content-Length or Transfer-Encoding header fields received
    TEXT[!MUST]:    in a successful response to CONNECT.

  SECTION: [OPTIONS](#section-9.3.7)
    TEXT[!SHOULD]:    A server generating a successful response to OPTIONS SHOULD send any
    TEXT[!SHOULD]:    header that might indicate optional features implemented by the
    TEXT[!SHOULD]:    server and applicable to the target resource (e.g., Allow), including
    TEXT[!SHOULD]:    potential extensions not defined by this specification.
    TEXT[!MAY]:    A client MAY send a Max-Forwards header field in an OPTIONS request
    TEXT[!MAY]:    to target a specific recipient in the request chain (see
    TEXT[!MAY]:    Section 7.6.2).
    TEXT[!MUST]: A proxy MUST NOT generate a Max-Forwards header
    TEXT[!MUST]:    field while forwarding a request unless that request was received
    TEXT[!MUST]:    with a Max-Forwards field.
    TEXT[!MUST]:    A client that generates an OPTIONS request containing content MUST
    TEXT[!MUST]:    send a valid Content-Type header field describing the representation
    TEXT[!MUST]:    media type.

  SECTION: [TRACE](#section-9.3.8)
    TEXT[!SHOULD]: The final recipient of the request SHOULD
    TEXT[!SHOULD]:    reflect the message received, excluding some fields described below,
    TEXT[!SHOULD]:    back to the client as the content of a 200 (OK) response.
    TEXT[!MUST]:    A client MUST NOT generate fields in a TRACE request containing
    TEXT[!MUST]:    sensitive data that might be disclosed by the response.
    TEXT[!SHOULD]: The final
    TEXT[!SHOULD]:    recipient of the request SHOULD exclude any request fields that are
    TEXT[!SHOULD]:    likely to contain sensitive data when that recipient generates the
    TEXT[!SHOULD]:    response content.
    TEXT[!MUST]:    A client MUST NOT send content in a TRACE request.

  SECTION: [Expect](#section-10.1.1)
    TEXT[!MAY]:    A server that receives an Expect field value containing a member
    TEXT[!MAY]:    other than 100-continue MAY respond with a 417 (Expectation Failed)
    TEXT[!MAY]:    status code to indicate that the unexpected expectation cannot be
    TEXT[!MAY]:    met.
    TEXT[!MUST]:    *  A client MUST NOT generate a 100-continue expectation in a request
    TEXT[!MUST]:       that does not include content.
    TEXT[!MUST]:    *  A client that will wait for a 100 (Continue) response before
    TEXT[!MUST]:       sending the request content MUST send an Expect header field
    TEXT[!MUST]:       containing a 100-continue expectation.
    TEXT[!MAY]:    *  A client that sends a 100-continue expectation is not required to
    TEXT[!MAY]:       wait for any specific length of time; such a client MAY proceed to
    TEXT[!MAY]:       send the content even if it has not yet received a response.
    TEXT[!SHOULD]:       Furthermore, since 100 (Continue) responses cannot be sent through
    TEXT[!SHOULD]:       an HTTP/1.0 intermediary, such a client SHOULD NOT wait for an
    TEXT[!SHOULD]:       indefinite period before sending the content.
    TEXT[!SHOULD]:    *  A client that receives a 417 (Expectation Failed) status code in
    TEXT[!SHOULD]:       response to a request containing a 100-continue expectation SHOULD
    TEXT[!SHOULD]:       repeat that request without a 100-continue expectation, since the
    TEXT[!SHOULD]:       417 response merely indicates that the response chain does not
    TEXT[!SHOULD]:       support expectations (e.g., it passes through an HTTP/1.0 server).
    TEXT[!MUST]:    *  A server that receives a 100-continue expectation in an HTTP/1.0
    TEXT[!MUST]:       request MUST ignore that expectation.
    TEXT[!MAY]:    *  A server MAY omit sending a 100 (Continue) response if it has
    TEXT[!MAY]:       already received some or all of the content for the corresponding
    TEXT[!MAY]:       request, or if the framing indicates that there is no content.
    TEXT[!MUST]:    *  A server that sends a 100 (Continue) response MUST ultimately send
    TEXT[!MUST]:       a final status code, once it receives and processes the request
    TEXT[!MUST]:       content, unless the connection is closed prematurely.
    TEXT[!SHOULD]:    *  A server that responds with a final status code before reading the
    TEXT[!SHOULD]:       entire request content SHOULD indicate whether it intends to close
    TEXT[!SHOULD]:       the connection (e.g., see Section 9.6 of [HTTP/1.1]) or continue
    TEXT[!SHOULD]:       reading the request content.
    TEXT[!MUST]:    Upon receiving an HTTP/1.1 (or later) request that has a method,
    TEXT[!MUST]:    target URI, and complete header section that contains a 100-continue
    TEXT[!MUST]:    expectation and an indication that request content will follow, an
    TEXT[!MUST]:    origin server MUST send either:
    TEXT[!MUST]:    The origin server MUST NOT wait for the content before sending the
    TEXT[!MUST]:    100 (Continue) response.
    TEXT[!MUST]:    Upon receiving an HTTP/1.1 (or later) request that has a method,
    TEXT[!MUST]:    target URI, and complete header section that contains a 100-continue
    TEXT[!MUST]:    expectation and indicates a request content will follow, a proxy MUST
    TEXT[!MUST]:    either:
    TEXT[!MAY]:    If the proxy believes (from configuration or past interaction) that
    TEXT[!MAY]:    the next inbound server only supports HTTP/1.0, the proxy MAY
    TEXT[!MAY]:    generate an immediate 100 (Continue) response to encourage the client
    TEXT[!MAY]:    to begin sending the content.

  SECTION: [From](#section-10.1.2)
    TEXT[!SHOULD]:    user agent SHOULD NOT send a From header field without explicit
    TEXT[!SHOULD]:    configuration by the user, since that might conflict with the user's
    TEXT[!SHOULD]:    privacy interests or their site's security policy.
    TEXT[!SHOULD]:    A robotic user agent SHOULD send a valid From header field so that
    TEXT[!SHOULD]:    the person responsible for running the robot can be contacted if
    TEXT[!SHOULD]:    problems occur on servers, such as if the robot is sending excessive,
    TEXT[!SHOULD]:    unwanted, or invalid requests.
    TEXT[!SHOULD]:    A server SHOULD NOT use the From header field for access control or
    TEXT[!SHOULD]:    authentication, since its value is expected to be visible to anyone
    TEXT[!SHOULD]:    receiving or observing the request and is often recorded within
    TEXT[!SHOULD]:    logfiles and error reports without any expectation of privacy.

  SECTION: [Referer](#section-10.1.3)
    TEXT[!MUST]: A user
    TEXT[!MUST]:    agent MUST NOT include the fragment and userinfo components of the
    TEXT[!MUST]:    URI reference [URI], if any, when generating the Referer field value.
    TEXT[!MUST]:    If the target URI was obtained from a source that does not have its
    TEXT[!MUST]:    own URI (e.g., input from the user keyboard, or an entry within the
    TEXT[!MUST]:    user's bookmarks/favorites), the user agent MUST either exclude the
    TEXT[!MUST]:    Referer header field or send it with a value of "about:blank".
    TEXT[!MAY]:    The Referer header field value need not convey the full URI of the
    TEXT[!MAY]:    referring resource; a user agent MAY truncate parts other than the
    TEXT[!MAY]:    referring origin.
    TEXT[!SHOULD]: A user agent SHOULD NOT send a Referer header field if
    TEXT[!SHOULD]:    the referring resource was accessed with a secure protocol and the
    TEXT[!SHOULD]:    request target has an origin differing from that of the referring
    TEXT[!SHOULD]:    resource, unless the referring resource explicitly allows Referer to
    TEXT[!SHOULD]:    be sent.
    TEXT[!MUST]: A user agent MUST NOT send a Referer header field in an
    TEXT[!MUST]:    unsecured HTTP request if the referring resource was accessed with a
    TEXT[!MUST]:    secure protocol.
    TEXT[!SHOULD]: An
    TEXT[!SHOULD]:    intermediary SHOULD NOT modify or delete the Referer header field
    TEXT[!SHOULD]:    when the field value shares the same scheme and host as the target
    TEXT[!SHOULD]:    URI.

  SECTION: [TE](#section-10.1.4)
    TEXT[!MUST]:    A sender of TE MUST also send a "TE" connection option within the
    TEXT[!MUST]:    Connection header field (Section 7.6.1) to inform intermediaries not
    TEXT[!MUST]:    to forward this field.

  SECTION: [User-Agent](#section-10.1.5)
    TEXT[!SHOULD]: A user agent SHOULD send a User-Agent header field in each
    TEXT[!SHOULD]:    request unless specifically configured not to do so.
    TEXT[!MUST]:    A sender SHOULD limit generated product identifiers to what is
    TEXT[!MUST]:    necessary to identify the product; a sender MUST NOT generate
    TEXT[!MUST]:    advertising or other nonessential information within the product
    TEXT[!MUST]:    identifier.
    TEXT[!SHOULD]: A sender SHOULD NOT generate information in
    TEXT[!SHOULD]:    product-version that is not a version identifier (i.e., successive
    TEXT[!SHOULD]:    versions of the same product name ought to differ only in the
    TEXT[!SHOULD]:    product-version portion of the product identifier).
    TEXT[!SHOULD]:    A user agent SHOULD NOT generate a User-Agent header field containing
    TEXT[!SHOULD]:    needlessly fine-grained detail and SHOULD limit the addition of
    TEXT[!SHOULD]:    subproducts by third parties.

  SECTION: [Allow](#section-10.2.1)
    TEXT[!MUST]: An origin server MUST generate an Allow
    TEXT[!MUST]:    header field in a 405 (Method Not Allowed) response and MAY do so in
    TEXT[!MUST]:    any other response.
    TEXT[!MUST]:    A proxy MUST NOT modify the Allow header field -- it does not need to
    TEXT[!MUST]:    understand all of the indicated methods in order to handle them

  SECTION: [Location](#section-10.2.2)
    TEXT[!MUST]:    If the Location value provided in a 3xx (Redirection) response does
    TEXT[!MUST]:    not have a fragment component, a user agent MUST process the
    TEXT[!MUST]:    redirection as if the value inherits the fragment component of the
    TEXT[!MUST]:    URI reference used to generate the target URI (i.e., the redirection
    TEXT[!MUST]:    inherits the original reference's fragment, if any).

  SECTION: [Server](#section-10.2.4)
    TEXT[!MAY]: An origin server MAY generate a Server header field in
    TEXT[!MAY]:    its responses.
    TEXT[!SHOULD]:    An origin server SHOULD NOT generate a Server header field containing
    TEXT[!SHOULD]:    needlessly fine-grained detail and SHOULD limit the addition of
    TEXT[!SHOULD]:    subproducts by third parties.

  SECTION: [Authentication Parameters](#section-11.2)
    TEXT[!MUST]:    Authentication parameters are name/value pairs, where the name token
    TEXT[!MUST]:    is matched case-insensitively and each parameter name MUST only occur
    TEXT[!MUST]:    once per challenge.

  SECTION: [Credentials](#section-11.4)
    TEXT[!SHOULD]:    Upon receipt of a request for a protected resource that omits
    TEXT[!SHOULD]:    credentials, contains invalid credentials (e.g., a bad password) or
    TEXT[!SHOULD]:    partial credentials (e.g., when the authentication scheme requires
    TEXT[!SHOULD]:    more than one round trip), an origin server SHOULD send a 401
    TEXT[!SHOULD]:    (Unauthorized) response that contains a WWW-Authenticate header field
    TEXT[!SHOULD]:    with at least one (possibly new) challenge applicable to the
    TEXT[!SHOULD]:    requested resource.
    TEXT[!SHOULD]:    Likewise, upon receipt of a request that omits proxy credentials or
    TEXT[!SHOULD]:    contains invalid or partial proxy credentials, a proxy that requires
    TEXT[!SHOULD]:    authentication SHOULD generate a 407 (Proxy Authentication Required)
    TEXT[!SHOULD]:    response that contains a Proxy-Authenticate header field with at
    TEXT[!SHOULD]:    least one (possibly new) challenge applicable to the proxy.

  SECTION: [Establishing a Protection Space (Realm)](#section-11.5)
    TEXT[!MAY]: If a prior request has been authorized,
    TEXT[!MAY]:    the user agent MAY reuse the same credentials for all other requests
    TEXT[!MAY]:    within that protection space for a period of time determined by the
    TEXT[!MAY]:    authentication scheme, parameters, and/or user preferences (such as a
    TEXT[!MAY]:    configurable inactivity timeout).
    TEXT[!MUST]:    For historical reasons, a sender MUST only generate the quoted-string
    TEXT[!MUST]:    syntax.

  SECTION: [WWW-Authenticate](#section-11.6.1)
    TEXT[!MUST]:    A server generating a 401 (Unauthorized) response MUST send a WWW-
    TEXT[!MUST]:    Authenticate header field containing at least one challenge.
    TEXT[!MAY]:    server MAY generate a WWW-Authenticate header field in other response
    TEXT[!MAY]:    messages to indicate that supplying credentials (or different
    TEXT[!MAY]:    credentials) might affect the response.
    TEXT[!MUST]:    A proxy forwarding a response MUST NOT modify any WWW-Authenticate
    TEXT[!MUST]:    header fields in that response.

  SECTION: [Authorization](#section-11.6.2)
    TEXT[!MUST]:    A proxy forwarding a request MUST NOT modify any Authorization header
    TEXT[!MUST]:    fields in that request.

  SECTION: [Proxy-Authenticate](#section-11.7.1)
    TEXT[!MUST]: A proxy MUST send at least
    TEXT[!MUST]:    one Proxy-Authenticate header field in each 407 (Proxy Authentication
    TEXT[!MUST]:    Required) response that it generates.

  SECTION: [Proxy-Authorization](#section-11.7.2)
    TEXT[!MAY]: A proxy MAY
    TEXT[!MAY]:    relay the credentials from the client request to the next proxy if
    TEXT[!MAY]:    that is the mechanism by which the proxies cooperatively authenticate
    TEXT[!MAY]:    a given request.

  SECTION: [Proactive Negotiation](#section-12.1)
    TEXT[!MAY]: In order to improve the
    TEXT[!MAY]:    server's guess, a user agent MAY send request header fields that
    TEXT[!MAY]:    describe its preferences.

  SECTION: [Quality Values](#section-12.4.2)
    TEXT[!MUST]:    A sender of qvalue MUST NOT generate more than three digits after the
    TEXT[!MUST]:    decimal point.

  SECTION: [Accept](#section-12.5.1)
    TEXT[!SHOULD]: Senders using weights
    TEXT[!SHOULD]:    SHOULD send "q" last (after all media-range parameters).
    TEXT[!SHOULD]: Recipients
    TEXT[!SHOULD]:    SHOULD process any parameter named "q" as weight, regardless of
    TEXT[!SHOULD]:    parameter ordering.

  SECTION: [Accept-Charset](#section-12.5.2)
    TEXT[!MAY]: A user agent MAY
    TEXT[!MAY]:    associate a quality value with each charset to indicate the user's
    TEXT[!MAY]:    relative preference for that charset, as defined in Section 12.4.2.

  SECTION: [Accept-Encoding](#section-12.5.3)
    TEXT[!MAY]:    Each codings value MAY be given an associated quality value (weight)
    TEXT[!MAY]:    representing the preference for that encoding, as defined in
    TEXT[!MAY]:    Section 12.4.2.
    TEXT[!SHOULD]: If a non-empty Accept-Encoding header field is present in
    TEXT[!SHOULD]:    a request and none of the available representations for the response
    TEXT[!SHOULD]:    have a content coding that is listed as acceptable, the origin server
    TEXT[!SHOULD]:    SHOULD send a response without any content coding unless the identity
    TEXT[!SHOULD]:    coding is indicated as unacceptable.
    TEXT[!MUST]: In order to avoid confusion with issues related to
    TEXT[!MUST]:    media types, servers that fail a request with a 415 status for
    TEXT[!MUST]:    reasons unrelated to content codings MUST NOT include the Accept-
    TEXT[!MUST]:    Encoding header field.

  SECTION: [Accept-Language](#section-12.5.4)
    TEXT[!MUST]: A user agent that
    TEXT[!MUST]:    does not provide such control to the user MUST NOT send an Accept-
    TEXT[!MUST]:    Language header field.

  SECTION: [Vary](#section-12.5.5)
    TEXT[!MUST]: A proxy MUST
    TEXT[!MUST]:    NOT generate "*" in a Vary field value.
    TEXT[!MUST]: To inform cache recipients that they MUST NOT use this response
    TEXT[!MUST]:        to satisfy a later request unless the later request has the same
    TEXT[!MUST]:        values for the listed header fields as the original request
    TEXT[!MUST]:        (Section 4.1 of [CACHING]) or reuse of the response has been
    TEXT[!MUST]:        validated by the origin server.
    TEXT[!SHOULD]:    An origin server SHOULD generate a Vary header field on a cacheable
    TEXT[!SHOULD]:    response when it wishes that response to be selectively reused for
    TEXT[!SHOULD]:    subsequent requests.

  SECTION: [If-Match](#section-13.1.1)
    TEXT[!MUST]:    An origin server MUST use the strong comparison function when
    TEXT[!MUST]:    comparing entity tags for If-Match (Section 8.8.3.2), since the
    TEXT[!MUST]:    client intends this precondition to prevent the method from being
    TEXT[!MUST]:    applied if there have been any changes to the representation data.
    TEXT[!MUST]:    When an origin server receives a request that selects a
    TEXT[!MUST]:    representation and that request includes an If-Match header field,
    TEXT[!MUST]:    the origin server MUST evaluate the If-Match condition per
    TEXT[!MUST]:    Section 13.2 prior to performing the method.
    TEXT[!MUST]:    An origin server that evaluates an If-Match condition MUST NOT
    TEXT[!MUST]:    perform the requested method if the condition evaluates to false.
    TEXT[!MAY]:    Instead, the origin server MAY indicate that the conditional request
    TEXT[!MAY]:    failed by responding with a 412 (Precondition Failed) status code.
    TEXT[!MAY]:    Alternatively, if the request is a state-changing operation that
    TEXT[!MAY]:    appears to have already been applied to the selected representation,
    TEXT[!MAY]:    the origin server MAY respond with a 2xx (Successful) status code
    TEXT[!MAY]:    (i.e., the change requested by the user agent has already succeeded,
    TEXT[!MAY]:    but the user agent might not be aware of it, perhaps because the
    TEXT[!MAY]:    prior response was lost or an equivalent change was made by some
    TEXT[!MAY]:    other user agent).
    TEXT[!MAY]:    A client MAY send an If-Match header field in a GET request to
    TEXT[!MAY]:    indicate that it would prefer a 412 (Precondition Failed) response if
    TEXT[!MAY]:    the selected representation does not match.
    TEXT[!MAY]:    A cache or intermediary MAY ignore If-Match because its
    TEXT[!MAY]:    interoperability features are only necessary for an origin server.

  SECTION: [If-None-Match](#section-13.1.2)
    TEXT[!MUST]:    A recipient MUST use the weak comparison function when comparing
    TEXT[!MUST]:    entity tags for If-None-Match (Section 8.8.3.2), since weak entity
    TEXT[!MUST]:    tags can be used for cache validation even if there have been changes
    TEXT[!MUST]:    to the representation data.
    TEXT[!SHOULD]: When a client desires to update one or more
    TEXT[!SHOULD]:    stored responses that have entity tags, the client SHOULD generate an
    TEXT[!SHOULD]:    If-None-Match header field containing a list of those entity tags
    TEXT[!SHOULD]:    when making a GET request; this allows recipient servers to send a
    TEXT[!SHOULD]:    304 (Not Modified) response to indicate when one of those stored
    TEXT[!SHOULD]:    responses matches the selected representation.
    TEXT[!MUST]:    When an origin server receives a request that selects a
    TEXT[!MUST]:    representation and that request includes an If-None-Match header
    TEXT[!MUST]:    field, the origin server MUST evaluate the If-None-Match condition
    TEXT[!MUST]:    per Section 13.2 prior to performing the method.
    TEXT[!MUST]:    An origin server that evaluates an If-None-Match condition MUST NOT
    TEXT[!MUST]:    perform the requested method if the condition evaluates to false;
    TEXT[!MUST]:    instead, the origin server MUST respond with either a) the 304 (Not
    TEXT[!MUST]:    Modified) status code if the request method is GET or HEAD or b) the
    TEXT[!MUST]:    412 (Precondition Failed) status code for all other request methods.

  SECTION: [If-Modified-Since](#section-13.1.3)
    TEXT[!MUST]:    A recipient MUST ignore If-Modified-Since if the request contains an
    TEXT[!MUST]:    If-None-Match header field; the condition in If-None-Match is
    TEXT[!MUST]:    considered to be a more accurate replacement for the condition in If-
    TEXT[!MUST]:    Modified-Since, and the two are only combined for the sake of
    TEXT[!MUST]:    interoperating with older intermediaries that might not implement
    TEXT[!MUST]:    If-None-Match.
    TEXT[!MUST]:    A recipient MUST ignore the If-Modified-Since header field if the
    TEXT[!MUST]:    received field value is not a valid HTTP-date, the field value has
    TEXT[!MUST]:    more than one member, or if the request method is neither GET nor
    TEXT[!MUST]:    HEAD.
    TEXT[!MUST]:    A recipient MUST ignore the If-Modified-Since header field if the
    TEXT[!MUST]:    resource does not have a modification date available.
    TEXT[!MUST]:    A recipient MUST interpret an If-Modified-Since field value's
    TEXT[!MUST]:    timestamp in terms of the origin server's clock.
    TEXT[!SHOULD]:    When an origin server receives a request that selects a
    TEXT[!SHOULD]:    representation and that request includes an If-Modified-Since header
    TEXT[!SHOULD]:    field without an If-None-Match header field, the origin server SHOULD
    TEXT[!SHOULD]:    evaluate the If-Modified-Since condition per Section 13.2 prior to
    TEXT[!SHOULD]:    performing the method.
    TEXT[!SHOULD]:    An origin server that evaluates an If-Modified-Since condition SHOULD
    TEXT[!SHOULD]:    NOT perform the requested method if the condition evaluates to false;
    TEXT[!SHOULD]:    instead, the origin server SHOULD generate a 304 (Not Modified)
    TEXT[!SHOULD]:    response, including only those metadata that are useful for
    TEXT[!SHOULD]:    identifying or updating a previously cached response.

  SECTION: [If-Unmodified-Since](#section-13.1.4)
    TEXT[!MUST]:    A recipient MUST ignore If-Unmodified-Since if the request contains
    TEXT[!MUST]:    an If-Match header field; the condition in If-Match is considered to
    TEXT[!MUST]:    be a more accurate replacement for the condition in If-Unmodified-
    TEXT[!MUST]:    Since, and the two are only combined for the sake of interoperating
    TEXT[!MUST]:    with older intermediaries that might not implement If-Match.

    TEXT[!MUST]:    received field value is not a valid HTTP-date (including when the
    TEXT[!MUST]:    field value appears to be a list of dates).
    TEXT[!MUST]:    A recipient MUST ignore the If-Unmodified-Since header field if the
    TEXT[!MUST]:    resource does not have a modification date available.
    TEXT[!MUST]:    A recipient MUST interpret an If-Unmodified-Since field value's
    TEXT[!MUST]:    timestamp in terms of the origin server's clock.
    TEXT[!MUST]:    When an origin server receives a request that selects a
    TEXT[!MUST]:    representation and that request includes an If-Unmodified-Since
    TEXT[!MUST]:    header field without an If-Match header field, the origin server MUST
    TEXT[!MUST]:    evaluate the If-Unmodified-Since condition per Section 13.2 prior to
    TEXT[!MUST]:    performing the method.
    TEXT[!MUST]:    An origin server that evaluates an If-Unmodified-Since condition MUST
    TEXT[!MUST]:    NOT perform the requested method if the condition evaluates to false.
    TEXT[!MAY]:    Instead, the origin server MAY indicate that the conditional request
    TEXT[!MAY]:    failed by responding with a 412 (Precondition Failed) status code.
    TEXT[!MAY]:    Alternatively, if the request is a state-changing operation that
    TEXT[!MAY]:    appears to have already been applied to the selected representation,
    TEXT[!MAY]:    the origin server MAY respond with a 2xx (Successful) status code
    TEXT[!MAY]:    (i.e., the change requested by the user agent has already succeeded,
    TEXT[!MAY]:    but the user agent might not be aware of it, perhaps because the
    TEXT[!MAY]:    prior response was lost or an equivalent change was made by some
    TEXT[!MAY]:    other user agent).
    TEXT[!MAY]:    A client MAY send an If-Unmodified-Since header field in a GET
    TEXT[!MAY]:    request to indicate that it would prefer a 412 (Precondition Failed)
    TEXT[!MAY]:    response if the selected representation has been modified.
    TEXT[!MAY]:    A cache or intermediary MAY ignore If-Unmodified-Since because its
    TEXT[!MAY]:    interoperability features are only necessary for an origin server.

  SECTION: [If-Range](#section-13.1.5)
    TEXT[!MUST]:    A client MUST NOT generate an If-Range header field in a request that
    TEXT[!MUST]:    does not contain a Range header field.
    TEXT[!MUST]: A server MUST ignore an If-
    TEXT[!MUST]:    Range header field received in a request that does not contain a
    TEXT[!MUST]:    Range header field.
    TEXT[!MUST]: An origin server MUST ignore an If-Range header
    TEXT[!MUST]:    field received in a request for a target resource that does not
    TEXT[!MUST]:    support Range requests.
    TEXT[!MUST]:    A client MUST NOT generate an If-Range header field containing an
    TEXT[!MUST]:    entity tag that is marked as weak.
    TEXT[!MUST]: A client MUST NOT generate an If-
    TEXT[!MUST]:    Range header field containing an HTTP-date unless the client has no
    TEXT[!MUST]:    entity tag for the corresponding representation and the date is a
    TEXT[!MUST]:    strong validator in the sense defined by Section 8.8.2.2.
    TEXT[!MUST]:    A server that receives an If-Range header field on a Range request
    TEXT[!MUST]:    MUST evaluate the condition per Section 13.2 prior to performing the
    TEXT[!MUST]:    method.
    TEXT[!MUST]:    A recipient of an If-Range header field MUST ignore the Range header

    TEXT[!SHOULD]: Otherwise, the
    TEXT[!SHOULD]:    recipient SHOULD process the Range header field as requested.

  SECTION: [When to Evaluate](#section-13.2.1)
    TEXT[!MUST]:    Except when excluded below, a recipient cache or origin server MUST
    TEXT[!MUST]:    evaluate received request preconditions after it has successfully
    TEXT[!MUST]:    performed its normal request checks and just before it would process
    TEXT[!MUST]:    the request content (if any) or perform the action associated with
    TEXT[!MUST]:    the request method.
    TEXT[!MUST]: A server MUST ignore all received preconditions
    TEXT[!MUST]:    if its response to the same request without those conditions, prior
    TEXT[!MUST]:    to processing the request content, would have been a status code
    TEXT[!MUST]:    other than a 2xx (Successful) or 412 (Precondition Failed).
    TEXT[!MUST]:    A server that is not the origin server for the target resource and
    TEXT[!MUST]:    cannot act as a cache for requests on the target resource MUST NOT
    TEXT[!MUST]:    evaluate the conditional request header fields defined by this
    TEXT[!MUST]:    specification, and it MUST forward them if the request is forwarded,
    TEXT[!MUST]:    since the generating client intends that they be evaluated by a
    TEXT[!MUST]:    server that can provide a current representation.
    TEXT[!MUST]: Likewise, a server
    TEXT[!MUST]:    MUST ignore the conditional request header fields defined by this
    TEXT[!MUST]:    specification when received with a request method that does not
    TEXT[!MUST]:    involve the selection or modification of a selected representation,
    TEXT[!MUST]:    such as CONNECT, OPTIONS, or TRACE.

    TEXT[!MUST]: Since there is no predefined
    TEXT[!MUST]:    limit to the length of content, recipients MUST anticipate
    TEXT[!MUST]:    potentially large decimal numerals and prevent parsing errors due to
    TEXT[!MUST]:    integer conversion overflows.

  SECTION: [Range](#section-14.2)
    TEXT[!MAY]:    A server MAY ignore the Range header field.
    TEXT[!MUST]:    A server MUST ignore a Range header field received with a request
    TEXT[!MUST]:    method that is unrecognized or for which range handling is not
    TEXT[!MUST]:    defined.
    TEXT[!MUST]:    An origin server MUST ignore a Range header field that contains a
    TEXT[!MUST]:    range unit it does not understand.
    TEXT[!MAY]: A proxy MAY discard a Range
    TEXT[!MAY]:    header field that contains a range unit it does not understand.
    TEXT[!MAY]:    A server that supports range requests MAY ignore or reject a Range
    TEXT[!MAY]:    header field that contains an invalid ranges-specifier
    TEXT[!MAY]:    (Section 14.1.1), a ranges-specifier with more than two overlapping
    TEXT[!MAY]:    ranges, or a set of many small ranges that are not listed in
    TEXT[!MAY]:    ascending order, since these are indications of either a broken
    TEXT[!MAY]:    client or a deliberate denial-of-service attack (Section 17.15).
    TEXT[!SHOULD]:    client SHOULD NOT request multiple ranges that are inherently less
    TEXT[!SHOULD]:    efficient to process and transfer than a single range that
    TEXT[!SHOULD]:    encompasses the same data.
    TEXT[!MAY]:    A server that supports range requests MAY ignore a Range header field
    TEXT[!MAY]:    when the selected representation has no content (i.e., the selected
    TEXT[!MAY]:    representation's data is of zero length).
    TEXT[!SHOULD]:    A client that is requesting multiple ranges SHOULD list those ranges
    TEXT[!SHOULD]:    in ascending order (the order in which they would typically be
    TEXT[!SHOULD]:    received in a complete representation) unless there is a specific
    TEXT[!SHOULD]:    need to request a later part earlier.
    TEXT[!SHOULD]:    If all of the preconditions are true, the server supports the Range
    TEXT[!SHOULD]:    header field for the target resource, the received Range field-value
    TEXT[!SHOULD]:    contains a valid ranges-specifier with a range-unit supported for
    TEXT[!SHOULD]:    that target resource, and that ranges-specifier is satisfiable with
    TEXT[!SHOULD]:    respect to the selected representation, the server SHOULD send a 206
    TEXT[!SHOULD]:    (Partial Content) response with content containing one or more
    TEXT[!SHOULD]:    partial representations that correspond to the satisfiable
    TEXT[!SHOULD]:    range-spec(s) requested.
    TEXT[!SHOULD]:    If all of the preconditions are true, the server supports the Range
    TEXT[!SHOULD]:    header field for the target resource, the received Range field-value
    TEXT[!SHOULD]:    contains a valid ranges-specifier, and either the range-unit is not
    TEXT[!SHOULD]:    supported for that target resource or the ranges-specifier is
    TEXT[!SHOULD]:    unsatisfiable with respect to the selected representation, the server
    TEXT[!SHOULD]:    SHOULD send a 416 (Range Not Satisfiable) response.

  SECTION: [Status Codes](#section-15)
    TEXT[implementation]:    The status code of a response is a three-digit integer code
    TEXT[implementation,test]: All valid status codes are within the
    TEXT[implementation,test]:    range of 100 to 599, inclusive.
    TEXT[implementation,test]:    The first digit of the status code defines the class of response.
    TEXT[!MUST]: However, a client MUST
    TEXT[!MUST]:    understand the class of any status code, as indicated by the first
    TEXT[!MUST]:    digit, and treat an unrecognized status code as being equivalent to
    TEXT[!MUST]:    the x00 status code of that class.
    TEXT[!SHOULD]:    A client that receives a response with an invalid status code SHOULD
    TEXT[!SHOULD]:    process the response as if it had a 5xx (Server Error) status code.

  SECTION: [Informational 1xx](#section-15.2)
    TEXT[!MUST]: Since HTTP/1.0 did not define any 1xx status codes, a
    TEXT[!MUST]:    server MUST NOT send a 1xx response to an HTTP/1.0 client.
    TEXT[!MUST]:    A client MUST be able to parse one or more 1xx responses received
    TEXT[!MUST]:    prior to a final response, even if the client does not expect one.
    TEXT[!MAY]:    user agent MAY ignore unexpected 1xx responses.
    TEXT[!MUST]:    A proxy MUST forward 1xx responses unless the proxy itself requested
    TEXT[!MUST]:    the generation of the 1xx response.

  SECTION: [101 Switching Protocols](#section-15.2.2)
    TEXT[!MUST]: The server MUST
    TEXT[!MUST]:    generate an Upgrade header field in the response that indicates which
    TEXT[!MUST]:    protocol(s) will be in effect after this response.

  SECTION: [200 OK](#section-15.3.1)
    TEXT[!SHOULD]:    In 200 responses to GET or HEAD, an origin server SHOULD send any
    TEXT[!SHOULD]:    available validator fields (Section 8.8) for the selected
    TEXT[!SHOULD]:    representation, with both a strong entity tag and a Last-Modified
    TEXT[!SHOULD]:    date being preferred.

  SECTION: [205 Reset Content](#section-15.3.6)
    TEXT[!MUST]:    Since the 205 status code implies that no additional content will be
    TEXT[!MUST]:    provided, a server MUST NOT generate content in a 205 response.

  SECTION: [206 Partial Content](#section-15.3.7)
    TEXT[!MUST]:    A client MUST inspect a 206 response's Content-Type and Content-Range
    TEXT[!MUST]:    field(s) to determine what parts are enclosed and whether additional
    TEXT[!MUST]:    requests are needed.
    TEXT[!MUST]:    A server that generates a 206 response MUST generate the following
    TEXT[!MUST]:    header fields, in addition to those required in the subsections
    TEXT[!MUST]:    below, if the field would have been sent in a 200 (OK) response to
    TEXT[!MUST]:    the same request: Date, Cache-Control, ETag, Expires,
    TEXT[!MUST]:    Content-Location, and Vary.
    TEXT[!SHOULD]:    A sender that generates a 206 response to a request with an If-Range
    TEXT[!SHOULD]:    header field SHOULD NOT generate other representation header fields
    TEXT[!SHOULD]:    beyond those required because the client already has a prior response
    TEXT[!SHOULD]:    containing those header fields.
    TEXT[!MUST]: Otherwise, a sender MUST generate
    TEXT[!MUST]:    all of the representation header fields that would have been sent in
    TEXT[!MUST]:    a 200 (OK) response to the same request.

  SECTION: [Single Part](#section-15.3.7.1)
    TEXT[!MUST]:    If a single part is being transferred, the server generating the 206
    TEXT[!MUST]:    response MUST generate a Content-Range header field, describing what
    TEXT[!MUST]:    range of the selected representation is enclosed, and a content
    TEXT[!MUST]:    consisting of the range.

  SECTION: [Multiple Parts](#section-15.3.7.2)
    TEXT[!MUST]:    If multiple parts are being transferred, the server generating the
    TEXT[!MUST]:    206 response MUST generate "multipart/byteranges" content, as defined
    TEXT[!MUST]:    in Section 14.6, and a Content-Type header field containing the
    TEXT[!MUST]:    "multipart/byteranges" media type and its required boundary
    TEXT[!MUST]:    parameter.
    TEXT[!MUST]: To avoid confusion with single-part responses, a server
    TEXT[!MUST]:    MUST NOT generate a Content-Range header field in the HTTP header
    TEXT[!MUST]:    section of a multiple part response (this field will be sent in each
    TEXT[!MUST]:    part instead).
    TEXT[!MUST]:    Within the header area of each body part in the multipart content,
    TEXT[!MUST]:    the server MUST generate a Content-Range header field corresponding
    TEXT[!MUST]:    to the range being enclosed in that body part.
    TEXT[!SHOULD]: If the selected
    TEXT[!SHOULD]:    representation would have had a Content-Type header field in a 200
    TEXT[!SHOULD]:    (OK) response, the server SHOULD generate that same Content-Type
    TEXT[!SHOULD]:    header field in the header area of each body part.
    TEXT[!MAY]:    When multiple ranges are requested, a server MAY coalesce any of the
    TEXT[!MAY]:    ranges that overlap, or that are separated by a gap that is smaller
    TEXT[!MAY]:    than the overhead of sending multiple parts, regardless of the order
    TEXT[!MAY]:    in which the corresponding range-spec appeared in the received Range
    TEXT[!MAY]:    header field.
    TEXT[!MUST]:    A server MUST NOT generate a multipart response to a request for a
    TEXT[!MUST]:    single range, since a client that does not request multiple parts
    TEXT[!MUST]:    might not support multipart responses.
    TEXT[!MAY]: However, a server MAY
    TEXT[!MAY]:    generate a "multipart/byteranges" response with only a single body
    TEXT[!MAY]:    part if multiple ranges were requested and only one range was found
    TEXT[!MAY]:    to be satisfiable or only one range remained after coalescing.
    TEXT[!MUST]:    client that cannot process a "multipart/byteranges" response MUST NOT
    TEXT[!MUST]:    generate a request that asks for multiple ranges.
    TEXT[!SHOULD]:    A server that generates a multipart response SHOULD send the parts in
    TEXT[!SHOULD]:    the same order that the corresponding range-spec appeared in the
    TEXT[!SHOULD]:    received Range header field, excluding those ranges that were deemed
    TEXT[!SHOULD]:    unsatisfiable or that were coalesced into other ranges.
    TEXT[!MUST]: A client
    TEXT[!MUST]:    that receives a multipart response MUST inspect the Content-Range
    TEXT[!MUST]:    header field present in each body part in order to determine which
    TEXT[!MUST]:    range is contained in that body part; a client cannot rely on
    TEXT[!MUST]:    receiving the same ranges that it requested, nor the same order that
    TEXT[!MUST]:    it requested.

  SECTION: [Combining Parts](#section-15.3.7.3)
    TEXT[!MAY]:    A client that has received multiple partial responses to GET requests
    TEXT[!MAY]:    on a target resource MAY combine those responses into a larger
    TEXT[!MAY]:    continuous range if they share the same strong validator.
    TEXT[!MUST]: If all of the matching stored responses
    TEXT[!MUST]:    are 206 responses, then the stored response with the most recent
    TEXT[!MUST]:    header fields is used as the source of header fields for the combined
    TEXT[!MUST]:    response, except that the client MUST use other header fields
    TEXT[!MUST]:    provided in the new response, aside from Content-Range, to replace
    TEXT[!MUST]:    all instances of the corresponding header fields in the stored
    TEXT[!MUST]:    response.
    TEXT[!MUST]: If the union consists of the entire range of the
    TEXT[!MUST]:    representation, then the client MUST process the combined response as
    TEXT[!MUST]:    if it were a complete 200 (OK) response, including a Content-Length
    TEXT[!MUST]:    header field that reflects the complete length.
    TEXT[!MUST]: Otherwise, the
    TEXT[!MUST]:    client MUST process the set of continuous ranges as one of the
    TEXT[!MUST]:    following: an incomplete 200 (OK) response if the combined response
    TEXT[!MUST]:    is a prefix of the representation, a single 206 (Partial Content)
    TEXT[!MUST]:    response containing "multipart/byteranges" content, or multiple 206
    TEXT[!MUST]:    (Partial Content) responses, each with one continuous range that is
    TEXT[!MUST]:    indicated by a Content-Range header field.
