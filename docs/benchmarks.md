# Benchmarks against warp

Run with `nix develop .#bench -c scripts/bench`. The same application
(bench/Hyperdrive.hs, bench/Warp.hs: a 13-byte response, a 1 MiB
response, and a 1 MiB upload whose length is returned) on hyperdrive
and on warp 3.4.9, both built with `-O2 -threaded` and run with
`+RTS -N8 -A32m`, the server on cores 0-7 and `wrk` (8 threads) on
cores 8-15. Each figure is one 10-second run: on this machine runs vary
by up to about 20%, and other work was running on it, so differences
smaller than that mean little.

## 2026-11-18, AMD Ryzen 9 9955HX (16 cores), after 21781f2 and the coarse timers

|---|---|---|

| small responses, 1000 connections | 407k (2.1 ms, 14 ms) | 745k (1.0 ms, 10 ms) |
| small responses, pipelined 16 deep | 722k (1.4 ms, 11 ms) | 931k (0.9 ms) |
| 1 MiB responses, 32 connections | 12.1k (2.4 ms, 8.3 ms) | 12.6k (2.4 ms, 6.6 ms) |
| 1 MiB uploads, 32 connections | 7.5k (3.8 ms, 12 ms) | 6.5k (3.8 ms, 78 ms) |
| memory per idle connection (10,000) | 17 KB | 22 KB |

The first run, before the coarse timers, gave hyperdrive 34k req/s on
small responses against warp's 595k: every wait and every write
registered with GHC's timer manager, and threads queued on its lock
(a quarter of the time was in pthread mutexes, with only 3 of 8 cores
busy). Without timers at all it reached 481k; with the coarse timers
(Hyperdrive.Server.Timer) it keeps every timeout and reaches 460k to
476k.

Next: small responses, where hyperdrive spends about 11 µs of CPU per
request to warp's 7.6 µs. Profile before changing anything.

## 2026-11-19, the small-response path profiled

Measured per request with 100 connections (perf, `+RTS -s`, strace,
/proc): hyperdrive used about 11.3 µs of CPU (4.7 user, 6.7 kernel),
warp 6.6 (1.8 user, 4.8 kernel). The pure core (`step` for a whole
exchange, single-threaded) costs 1.7 µs and allocates 6.9 KB; the rest
is the driver and the kernel. Changes, each measured:

- Shutdown is signalled through a `TVar` per connection, not one that
  every waiting connection read (its STM bookkeeping showed in perf).
- `Date` reads whole seconds from `getSystemTime`; `getPOSIXTime` went
  through Integer arithmetic on every response.
- The driver tries a non-blocking receive before waiting. System calls
  per request went from recv 1, writev 1, epoll_ctl 1, epoll_wait 0.9
  to recv 1, writev 1, epoll 0.03 each, as warp's.
- Each connection receives into one 16 KiB buffer and copies out what
  arrived. Allocation fell from 46 KB to 13 KB a request (warp: 5.8
  KB), and young-generation collections from 2,277 to 101 in 5 s; GC is
  now 7% of the time. The buffer costs memory: 26 KB per idle
  connection, from 17 (warp: 22).

CPU per request hardly moved (11.3 to 11.2 µs): what remains is spread
over the driver (about 3 µs of user time beyond the core) and the
kernel (about 2 µs more than warp's for the same system calls, not
explained yet; kernel profiling needs privileges this machine does not
give). Joining small writes into one buffer made no difference.

| | hyperdrive | warp |
|---|---|---|
| small responses, 100 connections | 449k req/s (p50 0.17 ms, p99 5.4 ms) | 691k (0.11 ms, 4.1 ms) |
| small responses, 1000 connections | 451k (1.2 ms, 62 ms) | 704k (1.1 ms, 42 ms) |
| small responses, pipelined 16 deep | 724k (1.2 ms, 7.2 ms) | 882k (1.0 ms, 7.3 ms) |
| 1 MiB responses, 32 connections | 11.1k (2.7 ms, 7.5 ms) | 11.4k (2.7 ms, 7.6 ms) |
| 1 MiB uploads, 32 connections | 8.2k (3.4 ms, 19 ms) | 6.0k (3.9 ms, 120 ms) |
| memory per idle connection (10,000) | 26 KB | 22 KB |

Then (same day): each connection waits on one `MVar` of its own,
filled by the event manager's one-shot callback when its socket is
readable, by the ticker when its timer expires, and by shutdown,
instead of an STM transaction over three `TVar`s (about a tenth of the
time in the profile). CPU per request 11.2 to 10.4-10.7 µs (user 4.6,
kernel 6.1); 490k-530k small responses a second in the local runs.

Then: a space leak. An in-process benchmark (requests generated by a
transport and served by `serveConnection`, no sockets) showed the live
heap growing with the number of requests on one connection, about 170
bytes each: the phase deadline was stored lazily, and referred to the
previous state, so each state kept the one before it alive for as long
as the connection lasted. Fixed (the deadline is evaluated before it is
stored), with a test that serves 60,000 requests on one connection and
checks the live heap stays flat. In process, a small request went from
3.75 to 2.95 µs (the pure core alone is 1.7); over sockets, about 554k
small responses a second, 10.2 µs of CPU each (user 4.3, kernel 6.2),
and GC fell from 1.6 s to 0.07 s per 5-second run.

Then: response heads rendered into one buffer of the exact size
(status lines precomputed per code, numbers without `show`, the `Date`
value made once a second and appended rather than the fields
rebuilt). In process, 2.95 to 2.4 µs a request, 10.3 to 9.0 KB.

## 2026-11-19 (night): the cost of header fields

A browser's request (13 fields) cost four times wrk's (one field). Two
changes, timed in process against ec75509 on a quiet machine
(alternating runs on one core; means):

| | minimal request | browser request |
|---|---|---|
| ec75509 | 2.31 µs | 9.88 µs |

## How to measure (tools kept from this work)

Timings need a quiet machine (ask first); allocation counts do not.

- `nix develop .#bench -c scripts/bench`: the comparison with warp
  over sockets (the tables above).
- `nix develop .#bench -c scripts/bench-cpu`: requests a second, and
  user and kernel CPU and page faults per request, for both servers.
- `bench-driver [N] [browser]` (in the bench shell, or built with
  `bench/local.project`): the driver and core in process, one
  connection, no sockets; time and bytes allocated per request, for
  wrk's request or a browser's. Pin it to a core
  (`taskset -c 2 bench-driver 300000 browser`). The quickest and
  steadiest measure of the server's own work.
- Comparing two commits: `git worktree add /tmp/before <commit>`, a copy
  of `bench/local.project` there, build `bench-driver` in each, and run
  them alternately several times (single runs vary by a few per cent).
- Allocation and GC: add `+RTS -s` to a run. Heap by closure type (no
  profiling build needed): `+RTS -hT -i0.2`, then read the `.hp` file;
  this is how the space leak was found (live heap growing with the
  number of requests).
- Where allocation and time go by function: a profiling build
  (`bench/local.project`, `--enable-profiling
  --profiling-detail=all-functions --builddir=dist-prof`), run with
  `+RTS -p`. Proportions only: profiling stops small functions from
  being inlined, so predicates like `isFieldVChar` show allocation they
  do not have in a normal build.
- CPU profiles: `nix shell nixpkgs#perf`, then `perf record -F 4000 -p
  PID -- sleep 4` while `wrk` runs, and `perf report --sort symbol`.
  Kernel symbols need `sudo sysctl kernel.perf_event_paranoid=1
  kernel.kptr_restrict=0` (restore with 2 and 1 afterwards); counting
  system calls with perf tracepoints also needs `/sys/kernel/tracing`
  readable. Without that, `strace -c -f` on a server started as its
  child (`ptrace_scope` 1 forbids attaching) counts system calls, at
  the cost of slowing it down.

## 2026-11-20: field lines without the line-by-line parse

The fast path for a valid head split the field section into lines and
ran each through `parseFieldLine`, which went over it about seven times
(the CRLF search, the tchar span, `isToken` again in `mkFieldName`, the
upper-case check, OWS stripped from each end, and `mkFieldValue`'s
scan), building a tuple and slices at each step. `scanFieldLines`
finds each line's end with one search for CR (memchr), takes the name
with one tchar span, and checks the value with one scan of plain
comparisons; anything it does not accept goes to the full path, as
before. Against abff6b4 on a quiet machine (`bench-driver 300000`,
alternating runs on one core, means of 5; allocation exact):

| | minimal request | browser request |
|---|---|---|
| abff6b4 | 2.436 µs, 9000 bytes | 9.019 µs, 18639 bytes |
| a single pass over each section, classifying octets with a 256-entry table | 2.403 µs, 8976 bytes | 9.121 µs, 14711 bytes |
| memchr for line ends and range checks for values (kept) | 2.262 µs, 8928 bytes | 7.306 µs, 15975 bytes |

The table version allocated least but was slower than before (its
times are from a round against abff6b4 at 2.373 and 8.816 µs): a
lookup and a mask for every octet lose to memchr and two comparisons.
A first draft of it, whose loop carried the field it would build as a
`where` binding, allocated 37600 bytes for the browser request: the
binding was rebuilt for every octet of the value.

Sharing common field names rather than copying them to lower case (a
table of 38 names by length, compared ignoring case; a name with no
capitals was already a slice, not a copy) saved 80 bytes per request on
the minimal request and 1055 on the browser's, but was slower against
91e894d (means of 5): minimal 2.268 to 2.376 µs, browser 7.265 to
7.659 µs; with the lookup kept out of line, 2.302 to 2.407 and 7.420 to
7.918. Not kept: copying a short name costs less than finding it. A
first version that searched with `filter` saved almost nothing, as
boxing the name for its closure cost what the copy did.

## 2026-11-20 (evening): yield before receiving

System calls per request under wrk (hello, 100 connections), counted
with perf tracepoints (`syscalls:sys_enter_*`, and `sys_exit_recvfrom`
filtered on `ret == -11`; needs `/sys/kernel/tracing` readable):

| per request | hyperdrive before | hyperdrive after | warp |
|---|---|---|---|
| `recvfrom` | 2.000 | 1.015 | 1.035 |
| of which found nothing (EAGAIN) | 0.999 | 0.015 | 0.035 |
| `epoll_ctl` | 1.000 | 0.015 | 0.035 |
| `epoll_wait` | 0.143 | 0.022 | 0.033 |
| `writev` / `sendto` | 1.000 | 1.000 | 1.000 |
| `futex` | 0.026 | 0.051 | 0.064 |

So warp did not wait more cheaply: it rarely waited. After sending a
response it calls `yield` (warp 3.4.9, `Network/Wai/Handler/Warp/HTTP1.hs`),
so the capability's other connections run first and the client's next
request has usually arrived when it receives. Hyperdrive's receive
straight after the response nearly always found nothing, and waiting
cost an `epoll_ctl` and a wake-up through the event manager. Now
`waitInput` yields when something was written since the last wait.

Small responses at 95% of warp (99% in `bench-cpu`), with a browser's
fields 90% (82% before), 1000 connections 93%; pipelined ahead by 4%.
The p99 at 1000 connections was 7.6 ms against warp's 6.8, so the tail
that looked worse after the yield (44 and 32 ms) was noise. The gap
left is user time, 0.3 µs a request; the kernel's is within 0.1 µs.

The chunked decoder used `breakSubstring` too, for each chunk-size
line and for the trailer section. With the same memchr searches
(`bench-driver chunked`: 16 chunks of 1 KiB, decoded and discarded;
alternating, means of 5, faster in every pair): 6.136 to 5.505 µs and
39699 to 36131 bytes a request. wrk's uploads send a Content-Length, so
`scripts/bench` does not see this.

Field values checked eight octets at a time (`allValueOctets`: a word
with no octet below 0x20 and none equal to 0x7F is valid; any other
goes to the octet loop, which allows HTAB). Against 8a21a45 on a quiet

Kept, by the user's decision: the minimal request's one short value
(15 octets) loses about 15 ns, the browser's twelve fields gain 150,
and longer values (cookies, user agents) gain more. A first version
allocated 624 bytes more a request: its loops were closures allocated

the worker (it was used only inside the loop, so GHC did not unbox it
without a bang).
