hyperdrive is a fast, low-level HTTP server written in
Haskell. hyperdrive will use a variety of techniques to ensure that it
provides a correct implementation and reliable performance.

This code is not yet fit for human consumption.


Requirements traceability
-------------------------

Conformance to the HTTP RFCs is tracked with
[duvet](https://github.com/awslabs/duvet). Code that implements a
requirement cites the exact text of the RFC:

    -- = https://www.rfc-editor.org/rfc/rfc9110#section-5.5
    -- # a recipient of CR, LF, or NUL within
    -- # a field value MUST either reject the message

Annotations in test modules are counted as tests. To generate the
compliance report in `.duvet/reports/`:

    nix develop -c duvet report

Checks
------

    nix flake check                      # build, run the test suites, check requirement coverage
    nix develop -c scripts/mutation-test # check that the tests catch deliberate bugs

`nix flake check` fails if a citation does not match its RFC, or if
requirement coverage changes without `.duvet/snapshot.txt` being
updated (run `nix develop -c duvet report` and commit the result).

Each package's `mutants` file lists deliberate bugs that its test
suite must catch. `scripts/mutation-test` applies each one in turn to
a temporary copy of the project and fails if any of them survives. It
takes several minutes, so CI runs it weekly rather than on every push.

Requirements that do not apply to hyperdrive, such as those for
clients, proxies, caches and IANA registrations, are recorded as duvet
exceptions in `.duvet/exceptions/`, each with a reason, so that the
report lists only what hyperdrive owes. They are generated by
`scripts/duvet-exceptions`, which classifies each requirement by the
subject of its sentence; decisions made by hand are recorded in that
script.

Design notes, including security requirements for the layers above
`hyperdrive-semantics`, are in `docs/design-notes.md`.
